# EspUsbHostDisplayTuring

> English: [README.md](README.md)

3.5インチのUSBスマートスクリーン（Turing Smart Screen revision A、および多数ある互換機）をLovyanGFXのpanelとして駆動します。

このパネルはCDCシリアルデバイス（`1a86:5722`、product `UsbMonitor`）として認識され、6バイトのコマンドとRGB565の矩形データを受け取ります。[`EspUsbHostDisplayDl1xx`](../../Vendor/EspUsbHostDisplayDl1xx/) と発想は同じ（USBディスプレイをLovyanGFXのpanelにする）ですが、トランスポートがまったく違います。両者の比較は [`docs/usb-display.ja.md`](../../../docs/usb-display.ja.md) にあります。

`.ino` には変更したい部分（何を描くか、パネルをどう設定するか）だけを置いています。パネル固有の処理は隣のヘッダにまとまっていて、そのまま他のプロジェクトへコピーできます。

| ファイル | 内容 |
|---|---|
| `TuringProtocol.hpp` | ワイヤ形式: 6バイトコマンドのパッキング、DISPLAY_BITMAPの矩形、向き、輝度、RGB565ピクセル。Arduino / LovyanGFX / USBに非依存 |
| `TuringDevice.hpp` | パネルの探索、line codingの設定、非同期CDC OUTキュー経由のコマンド／ピクセル送出 |
| `Panel_Turing.hpp` | `lgfx::Panel_Device` の派生クラスと `LGFX_Turing` |

## 必要なもの

- **LovyanGFX** と **LGFXVirtualCanvas 1.2.0以降**（差分転送が入ったバージョン）。どちらも `sketch.yaml` に記載済みです。
- `1a86:5722` として認識される3.5インチUSBスマートスクリーン。自身を `USB35INCHIPSV2` と名乗り、Turing Smart Screenのrevision Aプロトコルを話す個体です。ネイティブ解像度は320x480。
- 電源。バックライトが相応の電流を引くので、ホストボードがOTGコネクタに給電できない場合はセルフパワーハブか外部電源を使ってください。

## 仕組み

パネルは自前のフレームバッファを持ち、USB転送が完全に止まっても表示を保持します。定期的なリフレッシュは不要です。したがってLovyanGFX側のpanelもフレームバッファを持たず、描画操作はそのままDISPLAY_BITMAPの矩形＋ピクセル列になります。

このプロトコルに圧縮はありません。1ピクセルはつねに2バイトなので、320x480の全画面更新は内容によらず307,200バイトです。つまりこのサンプルは**転送律速**で、DL-1xxのサンプル（描画律速）とは逆になります。ここでLGFXVirtualCanvasが効いてきます。画面を水平バンドに分割して描くことで、差分転送が変化のないバンドを丸ごと省略でき、省略したバンドのバイトはそもそも送られません。

panelの色深度は `rgb565_nonswapped` 固定です。そのメモリ配置はリトルエンディアンRGB565、つまりワイヤ形式そのものなので、変換済みピクセルはバイトスワップなしでUSBに届きます。

サンプルのシーンの実測は **2 fps**、1フレームあたり画面の26%（153,600ピクセル中40,000、160 KB/s）を送出し、転送エラーは0でした。初回フレームは全画面を送るので約2秒かかります。

## このパネルが要求する2点

どちらもプロトコルの参照元には書かれておらず、しかも「一見動いているドライバ」に見える壊れ方をします。このコードを流用する前に知っておく価値があります。

**前の矩形のピクセルが届ききる前にコマンドを送ってはいけない。** どちらにせよパネルはバイトを消費し続けるので、エラーにもならず転送も失われません。コマンドとそれが開いた矩形が黙って捨てられるだけです。そこで `TuringDevice` はビットマップを同期の単位として扱います。開いている矩形に残っているピクセル数を数え、最後の1ピクセルが入った時点でリンクをドレインします。足りないまま終わった矩形は、残しておかずパディングします。パネルはピクセル数を自分で数えているので、足りないままだと次のコマンドをピクセルデータとして読んでしまうからです（発生した場合は `underfilled()` が報告します）。

これを省くと、バーストの最初の矩形しか表示されない画面になり、さらに矩形を増やすほどスループットが**上がって**見えます。大半が捨てられているからです。後述のバンドスイープはこれを検出するためのものです。

**コマンドは単独のUSB転送として送らなければならない。** パネルは転送の先頭からコマンドを取り出し、その転送の残りを無視します。そのためヘッダの後ろに詰めたペイロードは失われます。参照元のPython実装は `serial.write()` ごとに1転送になるため自然に満たしています。ここではヘッダを書いた直後に単独でpushしています。これを省くと、すべての矩形が数ピクセル横にずれて描かれ、あふれたピクセルが前の行に回り込みます。

## CDC OUTキュー

ディスプレイの書き手は、full-speedのbulk endpointが捌ける速度をはるかに超えてバイトを生成します。つまり押し戻し（backpressure）が要ります。`sendSerial()` 単体には押し戻しがありません。呼び出しごとに転送を確保してドライバに渡すだけなので、バスより速く書くとin-flightが増え続けてDMAメモリを食い潰します。

そこでこのサンプルは `serialWriteQueueBegin()` を呼び、転送を固定数だけ事前確保します。submitはノンブロッキングのままで、プールが埋まるとacquireがブロックします。これが経路全体のペースを決めます。バイトはプールのDMAバッファへ直接書きます。

```cpp
uint8_t *buffer = usb.serialWriteAcquire(&capacity, timeoutMs);
// ... 埋める ...
usb.serialWriteSubmit(buffer, length);
```

キューが有効な間は `sendSerial()` と `EspUsbHostCdcSerial::write()` もこのキューを通るので、既存のシリアルコードもそのまま押し戻しを受けられます。

## 速くするには

以下の数値はESP32-S3（full-speed USB）での `tests/manual/usb_display_turing` の実測です。同じホストはvendor bulkで1.098 MB/s出るので、ここでの上限はバスではなくパネル側です。

**送るピクセルを減らす。** 圧縮がない以上、変えられるのはこれだけです。パネルは約0.155 MB/sの固定レートで描くので、画面に出るまでの時間は「バイト数 ÷ そのレート」であり、バイト数は1ピクセル2バイトです。`setDiffMode(LGFXVirtualDiffMode::Tile)` は有効のままにし、動いた部分だけを描き直してください。

**分割の仕方は効かない。** 同じ307,200バイトは、1つの矩形で送っても96個に分けても同じ時間がかかります。

| 矩形数 | 各行数 | 時間 | レート |
|---|---|---|---|
| 1 | 480 | 1.883 s | 0.156 MB/s |
| 3 | 160 | 1.884 s | 0.156 MB/s |
| 8 | 60 | 1.884 s | 0.156 MB/s |
| 24 | 20 | 1.894 s | 0.155 MB/s |
| 48 | 10 | 1.911 s | 0.153 MB/s |
| 96 | 5 | 1.920 s | 0.153 MB/s |

24を超えたあたりからのわずかな低下は矩形ごとの往復ぶんです。既定の `setMemoryLimit(16 * 1024)`（1バンド約25行）が妥当なのはこのためで、往復が誤差になる程度に大きく、かつ差分転送が意味のある粒度で省略できる程度に小さい値です。ここを細かく調整しても得るものはほとんどありません。

この表が平坦ではなく**右肩上がり**になったら、矩形が描かれずに捨てられています。上記の2点を確認してください。

**キューの形も効かない。** 深さ3×4 KBと深さ4×8 KBは同じ数値になります。パネルは受け取ったぶんを消化するまでNAKするからです。プールはスループットのためではなく押し戻しのためにあるので、小さいままで構いません。

## 制限

- 回転はLovyanGFXではなくパネル側が行います。`setRotation()` は0に戻されます。`init()` の前に `TuringDevice::setOrientation()` を使ってください。
- 読み戻し不可（`isReadable()` は false）。`readRect()`、ARGB合成、画面内容を必要とする処理は動きません。
- `copyRect()` は何もしません。プロトコルに画面内コピーがなく読み戻しもできないため、実装しようがありません。
- 16 bppのみ。プロトコルに他のピクセル形式はありません。
- 同時に扱えるパネルは1台です。
- `COMMAND_RESET` はサンプルでは意図的に使っていません。パネルが再起動してUSB上で再認識されます。

## テスト

プロトコル層はhostのユニットテストで検証しています。パッキングのバグは実機では画像の乱れとしてしか見えないためです。

```sh
cd tests
uv run --env-file .env pytest unit/turing -v -s
```

実機のbring-up（向き、単色塗り、カラーバー、チェッカーボード、部分矩形、上記のバンドスイープ、表示保持、輝度）:

```sh
uv run --env-file .env pytest manual/usb_display_turing/usb_display_turing.py -v -s
```

Turing Smart Screenは各権利者の製品名です。本プロジェクトは当該ベンダーと提携・推奨・認定の関係にありません。ここで名前を使っているのは、これらのパネルが話すプロトコルを識別するためだけで、実際に検索される語がそれだからです。デバイス自身が名乗るモデル文字列は `USB35INCHIPSV2` で、このexampleが駆動するパネルの多くは別のブランドで売られています。
