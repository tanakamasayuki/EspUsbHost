## 2.7.9
- (EN) Make `end()` release the MSC volumes the instance still has mounted, and stop a rejected SYNCHRONIZE CACHE from failing an otherwise clean `mscUnmount()`. A mount owns a FatFs drive slot, a registered VFS path and one of the `CONFIG_FATFS_VOLUME_COUNT` (2 by default) `mscFatMounts` entries; only a disconnect released them, so tearing the host down with a volume still mounted left the entry behind, the next `mscMount()` of the same `basePath` was refused as already mounted, and the drive slots ran out after two cycles while the stale mount still routed FatFs reads at whatever device later took that address. `end()` now unmounts them before the tasks stop, so SYNCHRONIZE CACHE can still reach the device. That flush is best effort and its result was already ignored, but it used to leave `lastError()` reporting `ESP_FAIL` for an unmount that succeeded, which a normal teardown hits on any device that answers the command inconsistently (the Arduino `USBMSC` peer does); `mscUnmount()` now restores the previous error and leaves the logging and the per-device skip to `mscSynchronizeCache()`. New `usb_msc_fat` peer test: the peer formats its own 128 KB RAM disk with `f_mkfs()` and writes a file into it before USB comes up, so the volume comes from the same FatFs the host mounts it with, and the test covers mount/read/unmount, the reported mount-unmount-`end()`-`begin()`-remount sequence, and `end()` releasing a still-mounted volume.

- (EN) Fix `end()` leaving the ESP-IDF USB Host Library installed when the bus is empty, which made every later `begin()` fail with `ESP_ERR_INVALID_STATE`. `usb_host_uninstall()` refuses while the library still holds an unread event flag or a pending process request, and the last `usb_host_client_deregister()` sets `USB_HOST_LIB_EVENT_FLAGS_NO_CLIENTS`; only `usb_host_lib_handle_events()` clears it. Shutdown called that handler only while waiting for `ALL_FREE`, and `usb_host_device_free_all()` returns `ESP_OK` without an `ALL_FREE` event when the device list is empty, so with nothing attached nothing consumed `NO_CLIENTS`: the uninstall was rejected, the host library stayed installed, and `usb_host_install()` in the next `begin()` failed for good. `uninstallHostLibrary()` now retries `usb_host_uninstall()` while handling library events until it is accepted, which also covers a hub process request that freeing the last device can queue. Reported as issue #42 (mount an MSC volume, unmount, `end()`, `begin()`); the restart coverage added in 2.4.1 keeps a device attached through teardown, which takes the `ESP_ERR_NOT_FINISHED` path and never reached this. The `usb_msc` peer test now covers both: teardown with the device attached, and teardown while the peer is rebooting so the device list is empty, asserting `devices_before=0` so that case cannot silently stop being tested.

## 2.7.8
- (EN) Add `examples/HID/EspUsbHostMacroPadN3`, which drives a Mirabox N3 / Ajazz AKP03 family LCD macro pad from an ESP32-P4: it paints the six key screens, sets the backlight and reports key input, with no vendor software involved. The pad is a composite HID device whose interface 0 is vendor-defined and carries the pad's own `CRT` packet protocol on a 512-byte interrupt IN and a 1024-byte interrupt OUT endpoint, while interface 1 is an ordinary boot keyboard, so `onHIDVendorInput()` / `sendHIDVendorOutput()` cover it and nothing pad-specific is in the library. Key images are 64x64 JPEG, produced by the ESP32-P4's JPEG encoder peripheral from an RGB565 tile, which is why the profiles need `PSRAM=enabled` (the encoder allocates from PSRAM); the example is ESP32-P4 high-speed only because of the 1024-byte endpoint, and it sets `EspUsbHostConfig::fifo` accordingly. Verified on a STREONOR S6 (`1500:3006`, firmware `V3.S6.02.011`): the firmware-version read, brightness, clear, refresh, a JPEG on each of the six keys, the key order (1..3 then 4..6 in reading order), the quarter turn the panel applies to an uploaded tile, and that the `DIS` command is a shutdown announcement that makes the device leave the bus rather than a "wake the screen" call. The pad only becomes a host-driven device after a session handshake: it sends no input reports at all until the host sends `CRT..DIS`, and a session with no traffic ends with the pad detaching from the bus and re-enumerating half a minute later, so the sketch holds it open with the `CRT..CONNECT` keepalive every 5 s (the vendor application uses ~10 s). Outside a session the pad draws its own stored icon over a pressed key, so the sketch also repaints the key an event names. Input reports carry an `"ACK" 00 00 "OK" 00 00` header followed by a code and a state: `0x01..0x06` press/release for the LCD keys, `0x25`/`0x30`/`0x31` for the three scene keys, `0x90/0x91`, `0x60/0x61`, `0x50/0x51` for the three encoders' two turn directions, and `0x33`/`0x34`/`0x35` for an encoder push - all twelve controls worked through on the device in a known order, with encoder 1 the bottom-left knob, 2 the bottom-right and 3 the top one. They arrive through `onHIDInput()` rather than `onHIDVendorInput()`, because the vendor path only fires for a report whose first byte is the library's vendor report ID and these start with `"ACK"` instead. The session handshake, the keepalive interval and the report format were read out of a USB capture of the vendor application driving the same unit; which knob owns which code pair, the scene key codes, and what `QUCMD` does remain open, so the sketch prints raw report bytes next to each decoded event. Protocol sources and their licences are listed in the example's README.

- (EN) Make the `EspUsbHostCdcSerial` receive ring sizable from the sketch. It was a fixed 512-byte member array, and overflow drops the oldest byte with no error, so users hitting loss at high baud or on bursty devices had no option but to edit `EspUsbHost.h` in place -- 512 bytes is about 5.5 ms of traffic at 921600 baud, so any `loop()` that blocks on WiFi, SD, or a display refresh loses data. `setRxBufferSize(size)` now sizes the ring per instance; the buffer moved to the heap and is allocated by `begin()` (or early by `setRxBufferSize()` itself), so `sizeof(EspUsbHostCdcSerial)` no longer depends on the size, and `rxBufferSize()` reports the current value. The originally requested form -- `#define` in the `.ino` before `#include <EspUsbHost.h>` -- is deliberately not supported: the sketch and the library are separate translation units, so it would have changed the class layout on one side only, i.e. an ODR violation that links cleanly and corrupts memory at runtime. Prompted by a user report.

## 2.7.6
- (EN) Fix CDC-NCM receive losing whole NTBs once a device batches datagrams. The bulk IN path assumed every device->host NTB would fit a fixed 3200-byte buffer (TinyUSB's default `CFG_TUD_NCM_IN_NTB_MAX_SIZE`) and silently discarded anything larger, but NCM leaves `dwNtbInMaxSize` to the device unless the host lowers it with `SET_NTB_INPUT_SIZE`, which was never sent -- nor was `GET_NTB_PARAMETERS` ever read. A device advertising more (16 KB is common for real NICs and phone tethering) is therefore free to pack several datagrams into one NTB, which is exactly what devices start doing when traffic picks up: the link stays up, `txFails` stays 0, and every datagram in an oversized NTB is lost. Now the size is negotiated per device at open time -- cap the device with `SET_NTB_INPUT_SIZE` when `bmNetworkCapabilities` bit 3 offers it, otherwise size the receive buffer after the device's own maximum, bounded by the new `ESP_USB_HOST_NETWORK_NTB_IN_LIMIT` (16 KB, `-D` overridable) -- and the negotiated value is rounded down to a multiple of the bulk IN endpoint's max packet size, since ESP-IDF specifies IN transfer lengths as integer multiples of MPS and the old 3200 was 50 x 64 but not a multiple of 512, i.e. misaligned on a high-speed (ESP32-P4) link. `EspUsbHostNetworkStats` gains `ntbInSize` (the negotiated size) and `rxOversized` (NTBs dropped for exceeding it, previously invisible; the first one now also logs a warning). The NCM functional descriptor's `bcdNcmVersion` / `bmNetworkCapabilities` are decoded into `EspUsbHostNetworkInterfaceInfo`. Found while investigating an unrelated report, and reproduced on the peer rig: with a peer advertising 8192 and writing in bursts, device-to-host throughput was 0.098 Mbps with 2.2 s TCP stalls, against 3.20 Mbps for the same peer at 3200; after the fix the same configuration runs at 3.3-4.4 Mbps with `rxOversized=0`. The new `tests/peer/usb_ncm_throughput` peer test drives both directions under sustained load and keeps that peer configuration, because the existing `usb_ncm` test only ever produced one datagram per NTB and could not see this. Two paths ship unverified on hardware, both of which simply did not exist before: the `SET_NTB_INPUT_SIZE` branch, which needs a device advertising capability bit 3 (the EspUsbDevice peer advertises 0), and the high-speed (ESP32-P4) MPS rounding, since the NCM peer rig is full-speed only and a single-P4 loopback cannot pair an HS device with its FS host. ## 2.5.2
- (EN) Fix silent data corruption on bulk/interrupt IN transfers on ESP32-P4. ESP-IDF's HCD only invalidates an IN DMA buffer when the transfer completes and never writes it back beforehand, so cache lines left dirty by `usb_host_transfer_alloc()` (which zeroes the buffer) or by heap bookkeeping in the same memory can be evicted while the controller is writing, overwriting received data. The library now writes those lines back with `esp_cache_msync()` immediately before every IN submit. The MSC path was hit hardest because it allocates a fresh transfer for each command. Verified on ESP32-P4 with the new `tests/manual/msc_cache_coherency` test: 50 of 64 multi-sector reads were corrupted before the fix, 0 of 64 after it (three consecutive runs). The change compiles out on targets without cached DMA memory such as ESP32-S3.
- (JA) ESP32-P4でのbulk/interrupt IN転送のデータ化けを修正しました。ESP-IDFのHCDはIN用DMA bufferを転送完了時にinvalidateするだけで、DMA開始前のwrite backを行いません。そのため`usb_host_transfer_alloc()`のゼロクリアや同じメモリに対するheapの管理書き込みで残ったdirty cache lineがDMA中にevictされ、受信データを上書きすることがあります。本ライブラリはIN転送のsubmit直前に`esp_cache_msync()`でこれらのlineをwrite backするようにしました。MSCはコマンドごとにtransferを確保するため最も影響を受けていました。新規の`tests/manual/msc_cache_coherency`テストをESP32-P4実機で実行し、修正前は64回中50回のmulti-sector readが破損、修正後は3回連続で64回中0回であることを確認しています。ESP32-S3などDMAメモリがキャッシュされないターゲットでは、この処理はコンパイル時に除去されます。
