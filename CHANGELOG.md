# Changelog / 変更履歴

## Unreleased
- (EN) Count a MIDI interface in `EspUsbHostDeviceInfo::supported`. The flag was built from HID, CDC, audio, MSC and vendor-serial detection, and a MIDI streaming interface is seen by none of them: it is Audio class but has no streaming endpoint, feature unit or sample rate, so a working MIDI keyboard was reported as unsupported. Found by the new lifecycle listener test, whose MIDI-only peer reported `supported=0` while MIDI messages were arriving. The only code the flag gated was the keyboard LED report, itself guarded by `hasKeyboardInterface`, so nothing else changes; a sketch that filters on `device.supported` now sees MIDI devices.
- (JA) `EspUsbHostDeviceInfo::supported` がMIDI interfaceを数えるようにしました。このフラグはHID・CDC・audio・MSC・vendor-serialの検出から組み立てられていましたが、MIDI streaming interfaceはそのどれにも引っかかりません。Audio classではあるものの、streaming endpointもfeature unitもサンプルレートも持たないためです。結果として、正常に動作するMIDIキーボードがサポート外として報告されていました。新しいlifecycle listenerテストで、MIDIメッセージが届いているのにMIDI専用peerが `supported=0` を報告して発覚しました。このフラグが分岐していたのはキーボードLED送信だけで、そこは `hasKeyboardInterface` でも守られているため他の挙動は変わりません。`device.supported` で絞り込んでいるスケッチからはMIDIデバイスが見えるようになります。
- (EN) Add listener APIs for the remaining events an integration library cannot share with the sketch: `addDeviceConnectedListener()`, `addDeviceDisconnectedListener()` and `addMidiMessageListener()`. Same contract as the parsed-input listeners added in 2.4.0 -- the single `on*()` callback stays compatible and runs first, listeners run in registration order from a per-event snapshot, `removeListener()` takes any id from the shared id space, and add / remove from inside a callback takes effect on the next event. Device lifecycle gets its own capacity, `ESP_USB_HOST_MAX_LIFECYCLE_LISTENERS`, defaulting to 8 rather than the 4 of `ESP_USB_HOST_MAX_LISTENERS_PER_EVENT`: an input event is watched by however many observers care about that one event and plateaus, while lifecycle is watched by every subsystem that tracks devices, so its count scales with how many subsystems are built on the stack. ESP32KeyBridge already needs exactly 4 there -- one per adapter -- which would leave the sketch no slot at all. Connect is now reported through one internal dispatch point, so the hub address-scan path that picks up devices the enumeration event missed reaches listeners too, and the MIDI callback set is snapshotted once per bulk transfer instead of per 4-byte packet.
- (JA) 統合ライブラリがスケッチと共有できずに残っていたeventにlistener APIを追加しました（`addDeviceConnectedListener()` / `addDeviceDisconnectedListener()` / `addMidiMessageListener()`）。契約は2.4.0で追加したパース済み入力のlistenerと同じで、単一の `on*()` callbackは互換のまま最初に呼ばれ、listenerはeventごとのsnapshotから登録順に呼ばれ、`removeListener()` は共有ID空間のどのIDでも受け取り、callback内での追加・解除は次のeventから反映されます。device lifecycleは専用の上限 `ESP_USB_HOST_MAX_LIFECYCLE_LISTENERS`（既定8）を持ち、`ESP_USB_HOST_MAX_LISTENERS_PER_EVENT`（既定4）とは分けています。入力eventの購読者数はそのevent1つに関心のある数で頭打ちになりますが、lifecycleはデバイスを追跡するすべてのサブシステムが購読するため、必要数はstack上に載せたサブシステムの数に比例して増えるためです。ESP32KeyBridgeは既にadapter 1つずつでちょうど4件必要で、既定4のままではスケッチ用のslotが1つも残りません。接続の通知は内部の1箇所に集約したため、列挙eventで取りこぼしたデバイスを拾うハブaddress scanの経路もlistenerに届きます。MIDIのcallback集合は4 byteパケットごとではなくbulk転送ごとに1回snapshotします。
- (EN) Rebuild the noise row of `usb_display_throughput` once per frame. It was precomputed once at startup, so with diff transfer on every tile hash matched from the second frame, the whole screen was skipped, and the condition that is supposed to measure the RLE worst case measured nothing. Found on the ESP32-P4, where it reported 6.15 fps at 3.6% of the bus with zero pixels pushed. Corrected, the worst case is 4,209,523 bytes per frame -- matching both the arithmetic (8,100 commands of 519 bytes) and the checkerboard step of `usb_display_dl1xx` -- which puts the transfer ceiling at 0.27 fps for full speed and 9.08 fps for high speed. The ESP32-P4 measures 1.55 fps at 17.1% of the bus, so full speed is exactly transfer-bound in the worst case while high speed is limited by the encoder with the bus 83% idle. Re-running the whole sweep on the ESP32-S3 with the fix reproduces its published noise figure -- 0.27 fps, 100% pushed, 4,209,523 bytes in one frame, 99.8% of the bus -- so the same number now stands for the right reason. That re-run also fits a 96 KB tile (44 bands, 2.57 fps) where an earlier build could not, which moves the single-tile ceiling on an ESP32-S3 to somewhere between 96 and 128 KB and makes it a function of what else the sketch has allocated; the tables and the tile-geometry guidance are updated accordingly.
- (JA) `usb_display_throughput` のノイズ行をフレームごとに再生成するようにしました。従来は起動時に1回だけ事前計算していたため、差分転送を有効にすると2フレーム目以降はタイルのハッシュが一致して画面全体がスキップされ、RLEの最悪ケースを測るはずの条件が何も測っていませんでした。ESP32-P4で `pushed_px=0`・バス3.6%・6.15 fpsという値が出て発覚しました。修正後の最悪ケースは1フレーム4,209,523バイトで、計算値（519バイト×8,100コマンド）と `usb_display_dl1xx` の市松ステップの実測の両方に一致します。ここから転送上限はfull-speedで0.27 fps、high speedで9.08 fpsとなります。ESP32-P4の実測は1.55 fps・バス17.1%で、full-speedは最悪ケースでちょうど転送律速、high speedはバスが83%空いたままエンコーダが律速だと分かりました。修正後のコードでESP32-S3の19条件を取り直したところ、公開していたノイズの値（0.27 fps・pushed 100%・1フレーム4,209,523バイト・バス99.8%）が再現し、同じ数値が今度は正しい理由で得られました。この再計測では以前のビルドで確保できなかった96 KBタイル（44バンド・2.57 fps）が確保できており、ESP32-S3のシングルタイル上限は96〜128 KBの間で、かつスケッチの他の確保状況に依存することが分かりました。表とタイル形状の指針もこれに合わせて更新しています。
- (EN) Normalize `usb_display_throughput` against the bulk OUT ceiling of the board under test instead of a single hardcoded number, selected from `--profile`, and drop the full-speed figure the sketch printed on every target. Measured on an ESP32-P4 by `vendor_bulk_throughput`: 36.4 MB/s at high speed (async depth 2, 8 KB transfers), 33x the 1.098 MB/s full-speed ceiling, so the display sweep has no transfer-bound condition left there -- pseudo-random pixels, which saturate a full-speed bus, use 3.6% of a high-speed one and rise from 0.27 to 6.15 fps. Every knob keeps the same ranking because they all act on draw cost. The P4 figures are in the example README, together with the wiring they need: the adapter draws more than the P4 host port could supply, so a self-powered hub is required, and it must be the only device on that hub. A full-speed device sharing it that fails its downstream port reset makes ESP-IDF's own `ext_port` driver abort the host with an assert that no library code can intercept.
- (JA) `usb_display_throughput` の帯域使用率を、ハードコードした1つの値ではなく `--profile` から選んだ実機の bulk OUT 上限に対して計算するようにし、スケッチが全ターゲットで出力していたfull-speedの値を削除しました。`vendor_bulk_throughput` によるESP32-P4の実測はhigh speedで36.4 MB/s（async depth 2・8 KB転送）で、full-speedの1.098 MB/sの33倍です。このためP4では描画計測に転送律速の条件が残りません。full-speedではバスを飽和させる疑似ランダムピクセルもhigh speedでは3.6%しか使わず、0.27→6.15 fpsになります。各つまみの効き方の順序は、いずれも描画コストに作用するものなので変わりません。P4の数値と、それに必要な配線をexampleのREADMEに記載しました。アダプタの消費電流はP4のホストポートの給電では足りないためセルフパワードハブが必須で、かつそのハブにはアダプタ以外をつなげません。同居したfull-speedデバイスのダウンストリームポートリセットが失敗すると、ESP-IDF自身の `ext_port` ドライバがassertでホストを落とし、ライブラリ側では捕捉できません。

- (EN) Add ZLP handling for vendor bulk OUT: `vendorSetAutoZlp()` / `vendorAutoZlp()` / `vendorWriteZlp()`. The ADB example and its manual test now enable it instead of tracking the packet size and sending the ZLP themselves.

## 2.5.2
- (EN) Fix silent data corruption on bulk/interrupt IN transfers on ESP32-P4. ESP-IDF's HCD only invalidates an IN DMA buffer when the transfer completes and never writes it back beforehand, so cache lines left dirty by `usb_host_transfer_alloc()` (which zeroes the buffer) or by heap bookkeeping in the same memory can be evicted while the controller is writing, overwriting received data. Verified on ESP32-P4 with the new `tests/manual/msc_cache_coherency` test: 50 of 64 multi-sector reads were corrupted before the fix, 0 of 64 after it (three consecutive runs).
